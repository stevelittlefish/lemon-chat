Lemon-chat: full codebase review

Go backend, vanilla-JS frontend, schema and migrations. The working notes for this review are in docs/code_review_2026-11-02.md, with fix checkboxes.

B+

Decent quality. Better than decent, in fact.

The code is idiomatic, well commented, and light on dependencies, and it has real tests that pass cleanly under the race detector. All three high-severity issues from the June review (unsanitised markdown, notes IDOR, attachment IDOR) are fixed, along with most of that review's medium items.

The remaining problems are localised, not structural. They cluster around three themes: keeping users' data apart, deleting and copying rows now that uploads exist, and a few code paths that skip the model-provider layer. Three of the bugs below were confirmed with throwaway tests.

The three themes

Multi-user boundaries

The WebSocket hub sends every event to every logged-in user, and model-written HTML files are served from the app's own origin.

Row lifecycle vs foreign keys

Cleanup, user deletion and forking weren't updated when uploads and sessions gained foreign keys, so they now fail or silently drop data.

Provider bypass

Title generation and fetch_url summaries call /chat/completions directly, so they break on the OAuth / Responses server.

Findings

H1Model-written HTML files run as the logged-in userStored XSS via create_document plus a linkread

tools.go:72 stores .html documents as text/html, and attachments.go:132–161 serves them inline from the app's origin with no CSP or nosniff header.

How it goes wrong

A web page the model reads (or a shared character) injects instructions. The model creates x.html containing script, then writes [open](/api/attachments/N) in its reply. DOMPurify keeps relative links, the link opens in a new tab on the same origin, and the script can call the whole API as you. The artifact panel itself is safe; only opening the URL directly is the problem.

Fix

Send Content-Security-Policy: sandbox; default-src 'none'; … and X-Content-Type-Options: nosniff on attachment responses. The research report endpoint already does this (research_reports.go:455). Alternatively, force a download for anything that isn't an image, plain text or markdown.

H2Every WebSocket event goes to every userConversation titles and attachment names leak between accountsread

ws.go:48 broadcast() writes to every connection. The upgrade handler checks the session but throws the user id away, so the hub can't target anyone.

How it goes wrong

When another user's conversation gets auto-titled, your browser receives {"type":"conversation_titled","title":"…"}. The same goes for completion titles, generated image titles and filenames, and background changes. The README promises each user's conversations are private.

Fix

Store the user id per connection and give each Broadcast* a target user. Every caller already knows the owner. Do this together with M7.

M1Background cleanup breaks for good after one abandoned image uploadconfirmed

store/conversations.go:152 deletes messages and then conversations, but never their attachment rows, which have non-cascading foreign keys.

How it goes wrong

Start a chat, paste an image, and walk away without sending. Thirty minutes later the cleanup fails with FOREIGN KEY constraint failed. It keeps failing every minute, and because one statement covers all stale chats, none of them is ever cleaned up again. Unsent uploads and their files are never garbage-collected either.

Fix

Use one transaction: delete attachments, then messages, then conversations, and remove the files after commit (reuse the DeleteConversation logic). Add a sweep for old unlinked uploads.

M2Admin “delete user” fails for anyone who has ever logged inconfirmed

store/users.go:63 runs a bare DELETE FROM user. Sessions, conversations and characters all reference the user without cascade, so the request returns a 500. admin.go:235 deletes the avatar file before the failing call, so the account survives without its avatar.

Fix

Decide the policy (delete their conversations, reassign or delete their characters), do it in a transaction, and delete the avatar after commit. This can be done in application code without a destructive migration.

M3Forking a conversation drops your uploaded imagesconfirmed

store/conversations.go:228–235 only copies attachments matched by tool_call_id. Uploads are linked by message_id instead, so the fork shows no thumbnails and the model loses the images on the next turn.

Fix

Build an old-to-new message id map while copying messages, then copy upload attachments with the remapped message_id, source and status.

M4Auto-titles and fetch_url skip the provider layerBroken on auth = "oauth" / api = "responses" servers; failed titles retry every 30 s foreverread

tasks/titles.go:53,264 and tools_web.go:361 POST to APIBase + "/chat/completions" with the static API key. If your default model is on the ChatGPT/Codex server, titles never generate and fetch_url errors out. The title worker has no backoff, so it re-asks for every failing conversation on every 30-second tick.

Fix

Route both through llm.NewProvider with the server's token source, and remember failed conversations with a backoff.

M5An avatar upload can exhaust server memoryread

avatars.go:73 fully decodes any image under 5 MB. A tiny PNG that claims to be 30000×30000 pixels allocates gigabytes. Any logged-in user can trigger it.

Fix

Call image.DecodeConfig first and reject anything over about 40 megapixels.

M6fetch_url can reach your LAN and localhostCarried over from the June reviewread

tools_web.go:45 and research/web.go:41 fetch any URL the model supplies. That includes Home Assistant, the NVR, ComfyUI, router pages and anything on localhost. A prompt-injected page can have the model read an internal URL, then send the contents out in a second fetch's query string.

Fix

Add a dialer Control hook that refuses private, loopback and link-local addresses after DNS resolution (which also covers redirects), with a config switch to allow them if you want that.

M7WebSocket frames can interleave, and one dead tab slows requestsread

ws.go:184 writes each frame as two separate writes, from many goroutines at once, with no lock. Pong replies are written concurrently too. Interleaved frames corrupt the stream and force reconnects. Broadcasts also run synchronously in the request handler, with a 5-second timeout per stalled client.

Fix

Give each client a writer goroutine with a buffered channel. That fixes both problems, and fits naturally with H2.

M8A model stream that dies halfway counts as a successread

llm/provider.go:504 discards the stream error once any text has arrived. The truncated answer is saved as a complete message, nothing is written to model_errors.log (contrary to AGENTS.md), and the user gets no warning. A mid-answer timeout behaves the same way.

Fix

Return the partial completion together with the error. Keep the partial text, but send an SSE error event and flush the error log.

L1The last tool-loop round runs tools and then throws the results awayread

messages.go:330–342: when the limit is hit, the tools still execute (images, notes) but the model is never asked to answer. Often nothing is saved and the user sees no reply. On the final round, send the request without tools so the model has to answer.

L2Accounts without a password accept any passwordread

auth.go:35, and bootstrap creates a passwordless admin if admin_password is unset. That's fine on localhost but risky on a LAN. At least log a loud warning at startup.

L3PUT /api/notes overwrites read-only notesread

The UI disables editing, but the API path through UpsertNoteAdmin ignores the lock. Require an explicit read_only: false to unlock.

L4Message order depends on SQLite's sort being stabletested

Messages are ordered by a timestamp with one-second resolution, and fork gives every copied message the same timestamp. It works today (a test with 300 forked messages kept their order), but add , id to the ORDER BY.

L5No server timeouts or request body limitsread

main.go:75 uses bare ListenAndServe: no header timeout and no graceful shutdown. JSON and multipart bodies have no size cap.

L6Some “not found” cases return a 500read

Attachment queries return sql.ErrNoRows where the rest of the store uses ErrNotFound. A deleted character also gives a 500 when you send a message.

L7Streaming re-renders the whole message on every tokenread

thread.js:573 runs a full markdown, sanitise and KaTeX pass on every token. Long answers get janky and you can't select text mid-stream. Render at most once per animation frame.

L8Client SSE parsing hides UI exceptionsread

api.js:22: the try/catch meant for JSON.parse also swallows errors thrown by event handlers.

L9A bad tool-call index from the model server can exhaust memoryread

provider.go:491 grows a slice up to whatever index the server sends. Cap it.

L10Small authorisation and robustness nitsread
  • Private characters' avatars are served to anyone who is logged in.
  • Creating or importing a conversation doesn't validate character_id visibility or model up front.
  • Conversation delete calls RemoveAll on a stored path with no check that it's inside attachments/.
  • Unchecked w.(http.Flusher) assertions will panic if middleware ever wraps the writer.
  • Note-pack import isn't transactional.
L11Logging has drifted from the project conventionread

Some lines use auth:, characters: and server: prefixes on handler logs, and admin create, update and delete user log nothing at all.

Maintainability

  • Two ways to call a model. llm.ChatComplete(url, key) lives alongside the Provider interface, and it's the root cause of M4. Fold the remaining callers into the Provider.
  • http.DefaultClient is used in 8 places, with no shared transport or timeouts. Inject a client, which is also where the SSRF guard should go.
  • Large mixed-concern files. thread.js (1302 lines) holds the artifact panel, lightbox, picker, streaming and scroll logic. researcher.go (1604), research-app.js (1179) and research.go (1060) are also big. Splitting thread.js into lightbox, artifact-panel and picker modules would match the project's one-concern-per-file rule.
  • The AGENTS.md code layout is stale. It's missing internal/llm, openai_auth, searx, redditimport, htmltext, the tools_*.go and research_*.go files, and more. Agents rely on that map.
  • Migrations aren't wrapped in transactions. If a two-statement step fails halfway, the next start fails with “duplicate column”.
  • Repo weight. benchmark/ (4.4 MB of model output) and the choose-your-own adventure docs aren't source code.
  • Test gaps. The store, llm and research packages are well tested. The chat send path has only helper-level tests and the frontend has none. A small “create, then delete/fork/clean up” store test would have caught all three confirmed bugs.

What's good

  • The June review's findings were actually fixed, not just noted.
  • Dependency discipline: 4 direct Go dependencies, a minimal hand-rolled WebSocket, and no frontend build step.
  • Comments explain non-obvious decisions, e.g. the nil *os.File in an interface, lexicographic RFC3339 session sweeps, and the Codex session header.
  • Careful migrations: the research_job rebuild runs in a transaction with a foreign-key check, and FKs, WAL and busy timeout are all on.
  • The research engine checkpoints and resumes after a crash, bounds its concurrency, and serves generated HTML reports under a sandbox CSP.
  • The provider layer writes redacted wire transcripts and keeps an always-on error log.
  • The frontend escapes consistently in template literals, sanitises all markdown with DOMPurify, and writes progress text via textContent.

Suggested order

  1. H1: one block of response headers.
  2. H2 + M7 together: a per-user hub with a writer goroutine per client.
  3. M1, M2, M3: store fixes, each with a regression test.
  4. M4, M8: provider consolidation, title backoff, honest stream errors.
  5. M5, M6, L5: hardening.
  6. The rest as convenient, plus refreshing the AGENTS.md layout.
