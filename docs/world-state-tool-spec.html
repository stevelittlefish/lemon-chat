World State Tool — Spec

Design and implementation spec for the session state store • June 2026

A general-purpose key-value store that gives the LLM a reliable memory for the current session. Covers stats (HP, gold), conditions (poisoned, exhausted), flags (talked to the old man), and inventory (torches, rope) — all as named values in one flat store.

Why one store, not three tools: Stats, conditions, and inventory are structurally identical — named values. The only distinction is semantic. A single flat store with four operations is simpler to implement, simpler for the LLM to use, and leaves the organisational choices (naming conventions, grouping) to whoever is writing the character prompt.

Persistence

Scope

State is scoped to a conversation. Each conversation has its own isolated key-value store. Starting a new conversation starts with an empty store — there is no automatic carry-over between sessions.

This is the right default for RPG sessions: each adventure starts fresh. If persistent world state across conversations is needed later, that belongs in the note store (a separate, future tool).

Database schema

One new table, added as a migration. Keys are unique per conversation — setting an existing key overwrites it. 

CREATE TABLE conversation_state (
    id              INTEGER PRIMARY KEY,
    conversation_id INTEGER NOT NULL REFERENCES conversation(id) ON DELETE CASCADE,
    key             TEXT NOT NULL,
    value           TEXT NOT NULL,
    updated_at      TEXT NOT NULL,
    UNIQUE(conversation_id, key)
);

CREATE INDEX conversation_state_conversation_id
    ON conversation_state(conversation_id);

All values are stored as TEXT. Numbers are stored as their string representation ("7", "3.5"). The state_modify operation parses the stored value as a number, applies the delta, and writes the result back. If the stored value cannot be parsed as a number, state_modify returns an error.

Lifecycle

  • State is created the first time state_set is called in a conversation.
  • State persists for the lifetime of the conversation row — it survives server restarts.
  • When a conversation is deleted, its state is deleted via ON DELETE CASCADE.
  • There is no automatic expiry or session timeout.
  • State can be inspected at any point with state_list.

Numeric storage

When state_modify writes a result back, it stores the number cleanly:

  • If the result is a whole number, store as an integer string: "7" not "7.0".
  • If the result has a fractional part, store as a decimal string: "3.5".

This means state_list output is always human-readable and the LLM can interpret it without needing to strip trailing zeros.

Operations

Four tool functions. Each is a separate tool definition in the registry, but all are toggled together as a group in the character editor UI.

state_set state_set(key: string, value: string)

Creates or overwrites a named value. Use for initial setup, resetting a value, or storing anything that is not a numeric delta.

Parameters

keystringName of the value. Non-empty. Any string is valid.
valuestringThe value to store. Use numeric strings for anything you intend to modify later.

Returns

Empty string on success. The LLM does not need to acknowledge the result.

Errors

  • Empty key
  • Empty value — use state_unset to remove a key

Examples

-- Set up a character sheet at the start of a session
state_set("HP", "10")
state_set("max HP", "10")
state_set("gold", "5")
state_set("torches", "3")

-- Mark a condition
state_set("poisoned", "yes")

-- Record a story flag
state_set("talked to old man", "yes")

-- Store free text — values are not limited to numbers or single words
state_set("quest", "find the stolen crown before dawn")

-- Overwrite an existing value
state_set("HP", "10")  -- resets HP to full after a rest
state_modify state_modify(key: string, delta: number)

Adds a numeric delta to an existing value. This is the operation that justifies having a server-side tool at all — it reads, computes, and writes atomically, so the LLM never has to do arithmetic or trust its own memory of the previous value.

Use a positive delta to increase, negative to decrease. The key must already exist and its current value must be parseable as a number.

Parameters

keystringName of the value to modify. Must exist.
deltanumberAmount to add. Negative values subtract.

Returns

The new value as a string, e.g. 7. The LLM can use this directly in narration.

Errors

  • Key not found — must state_set first
  • Current value is not numeric — cannot modify a text value
Why not auto-initialise to 0? Requiring an explicit state_set before state_modify means the LLM must make a conscious decision about the starting value. Auto-initialising to 0 would hide setup mistakes and make state_list output harder to trust.

Examples

-- Player takes 3 damage
state_modify("HP", -3)   → "7"

-- Player finds gold
state_modify("gold", +12)  → "17"

-- Player uses a torch
state_modify("torches", -1)  → "2"

-- Error: key doesn't exist yet
state_modify("arrows", -1)
→ error: key "arrows" not found — use state_set to initialise it first

-- Error: value is not numeric
state_modify("poisoned", -1)
→ error: value "yes" is not a number — use state_set to change text values
state_unset state_unset(key: string)

Removes a key entirely. Use when a condition clears, an item is fully consumed, or a flag is no longer relevant.

Parameters

keystringName of the value to remove.

Returns

Empty string on success. Returns an error if the key does not exist — this is intentional, to catch cases where the LLM thinks it is removing something that was never set.

Examples

-- Condition clears after a rest
state_unset("poisoned")

-- Item fully used up
state_modify("torches", -1)  → "0"
state_unset("torches")  -- remove now it's depleted

-- Error: key doesn't exist
state_unset("rope")
→ error: key "rope" not found
state_list state_list()

Returns all current state for the conversation as a formatted list. The LLM should call this at the start of each turn in a stateful session to reorient itself — it is the single source of truth for what is currently true in the world.

Results are returned in insertion order (oldest first), so a character sheet set up at the start of the session will always appear at the top.

Parameters

None.

Returns

One key: value pair per line. If the store is empty, returns No state stored.

Examples

state_list()

HP: 7
max HP: 10
gold: 17
torches: 2
quest: find the stolen crown before dawn
poisoned: yes
talked to old man: yes

-- Empty store
state_list()
No state stored.
Recommended system prompt instruction: Tell the character to call state_list silently at the start of each player turn before composing a response. This keeps the LLM grounded without the player seeing any machinery. The call is collapsed in the UI — only the narration is visible.

Naming Conventions

The store is a flat namespace — there are no categories or sub-stores. Naming conventions are a matter of character prompt style, not enforcement. Some reasonable approaches:

Flat readable names

Simple, works well for short sessions. The character prompt describes the conventions.

HP: 7
gold: 12
poisoned: yes
rusty key: 1
talked to guard: yes

Prefixed names

Useful if state_list output needs to be scanned quickly in a longer session.

stat.HP: 7
stat.gold: 12
cond.poisoned: yes
item.rusty key: 1
flag.talked to guard: yes

Either approach works. The LLM should be consistent within a session. The character's system prompt should specify which convention to use, or leave it to the LLM's discretion.

A Full Session Example

How the tool calls flow through a short exchange, all collapsed and invisible to the player.

--- Session starts ---

state_set("HP", "10")
state_set("max HP", "10")
state_set("gold", "5")
state_set("torch", "2")
state_set("rope", "1")

--- Player: "I search the goblin" ---

state_list()   -- LLM reorients
state_modify("gold", +3)   → "8"
-- LLM narrates: "You find 3 gold coins on the goblin. You now have 8."

--- Player: "I go north into the dark passage" ---

state_list()   -- LLM reorients
state_modify("torch", -1)   → "1"
-- LLM narrates: "You light a torch. One remaining."

--- Player fights a spider, gets poisoned ---

state_list()
state_modify("HP", -4)     → "6"
state_set("poisoned", "yes")
-- LLM narrates: "The spider bites you. You're poisoned. HP: 6/10."

--- Player rests at a shrine ---

state_list()
state_set("HP", "10")
state_unset("poisoned")
-- LLM narrates: "The shrine's magic cleanses the poison. You are restored."

--- End of session state_list ---

HP: 10
max HP: 10
gold: 8
torch: 1
rope: 1
talked to guard: yes

UI — Tool Groups

The world state tool is made up of four separate tool definitions in the registry (state_set, state_modify, state_unset, state_list). These are always enabled or disabled together — enabling "world state" means enabling all four. It would not make sense to enable state_modify without state_set.

This is the first tool that makes a flat checkbox list genuinely awkward. As more tools are added, grouping becomes necessary. The character edit page should organise tools into named groups, each with a master toggle.

Proposed groups

GroupToolsNotes
General get_time, roll_dice, pick_random, fetch_url, create_document Broadly useful, no external dependencies
Search & Knowledge searxng, wikipedia_search, wikipedia_get_page SearXNG requires config; Wikipedia does not
Image Generation generate_image_sdxl, generate_image_flux Both require ComfyUI config
World State state_set, state_modify, state_unset, state_list Always enabled/disabled as a unit

Future tools (note store, checklist, countdown) would slot into World State or form their own group if distinct enough.

Group toggle behaviour

  • The group header has a checkbox that enables or disables all tools in the group at once.
  • Groups where all tools require the same external config (image generation) can show one config hint at the group level rather than per tool.
  • Groups where some tools are unconfigured (e.g. SearXNG within Search & Knowledge) show the hint on the individual tool, not the group header.
  • Toggling a group on does not override individual tool state — if the user had previously disabled fetch_url individually, toggling "General" on should not re-enable it. Toggling off does disable all tools in the group.
Implementation note: World State tools should be stored in the character's tools array as a single entry "world_state", not as four separate IDs. The server expands "world_state" into the four tool definitions when building the request. This keeps the DB clean and makes it trivial to add a new state operation later without touching every existing character record.

Implementation Checklist

  1. Add conversation_state table as a new migration in internal/store/store.go.
  2. Add store functions in internal/store/conversations.go (or a new state.go): SetState, ModifyState, UnsetState, ListState.
  3. Add four tool definitions to toolRegistry in internal/server/tools.go.
  4. Add four executors to executors in tools.go.
  5. Add "world_state" as a compound tool ID that ToolDefsForCharacter expands into the four definitions.
  6. Add ToolMeta entry to allTools in InitTools.
  7. Update the character edit page to render tools in groups with group-level toggles.
  8. Update ToolContext to carry ConversationID and Store (both already present — verify they are passed through to these executors).

Spec ends here. The four operations are small and the DB schema is trivial — the most significant work is the UI grouping on the character edit page.
