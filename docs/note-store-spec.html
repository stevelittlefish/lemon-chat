Note Store — Spec

Persistent and session-scoped long-form notes for LLM tool use • June 2026

The note store gives an LLM a place to write and retrieve free-form text that persists beyond the context window. It is designed for lorebooks, world-building notes, NPC descriptions, scene summaries, and anything the model needs to recall accurately across a long session or across multiple sessions.

Contrast with world state. The existing state_set / state_modify tools handle short named values — HP, gold, conditions, boolean flags. Notes are for longer prose content that is written once and read back whole: lore entries, character descriptions, session briefs. Do not use notes for values the model will increment or compare numerically.

Key Format

Every note is identified by a key. Keys encode their scope in a mandatory prefix and use dot notation to express hierarchy.

Allowed characters

After the prefix, keys may contain lowercase letters (a–z), digits (0–9), underscores (_), hyphens (-), and full stops (.) used as segment separators. No uppercase, no spaces, no other punctuation.

Structural rules

  • Must begin with exactly one of: g., u., c.
  • Must have at least one character after the prefix
  • Must not end with a full stop
  • Must not contain two consecutive full stops

Validation regex

^(g|u|c)\.([a-z0-9_-]+\.)*[a-z0-9_-]+$

Examples

KeyValidReason
g.eldoriaYesGlobal note, single segment
g.eldoria.bestiaryYesGlobal note, two segments
u.quest_logYesUser note with underscore
c.eldoria.the_great_lakeYesConversation note, two segments
u.my-character.backstoryYesHyphen is allowed
eldoriaNoMissing prefix
g.EldoriaNoUppercase not allowed
g.eldoria.NoTrailing full stop
g.eldoria..bestiaryNoConsecutive full stops
g.NoNothing after prefix

Scopes

The prefix determines where a note lives, who can see it, and who can write to it. The three scopes are mutually exclusive — a note belongs to exactly one.

Prefix Scope Lifetime Readable by Writable by
g. Global Forever (manual delete only) Any user, any LLM session Any user or LLM (unless read-only)
u. User Until the user is deleted That user and their LLM sessions only That user or their LLM sessions (unless read-only)
c. Conversation Until the conversation is deleted Sessions within that conversation only Sessions within that conversation (unless read-only)
Scope is encoded in the key. The server derives scope purely from the prefix — there is no separate scope parameter in tool calls. A tool call that writes u.quest_log always goes to the current user's note store; c.notes always goes to the current conversation. The caller never needs to pass context separately.

Prefix search expansion

note_list accepts a bare search term without a prefix (e.g. eldoria). The server expands this into a search across all three scopes: it looks for g.eldoria, u.eldoria, and c.eldoria and their children, filtered to notes the caller can see. This lets the model discover all lore related to a topic without knowing in advance which scope it lives in.

If the search term already has a prefix (e.g. g.eldoria), only that scope is searched.

Value Handling

Note values are free-form text with no size limit imposed by the schema. In practice, values should be kept to what can be usefully retrieved in a single tool result — very large notes will consume context budget when loaded.

Trimming: leading and trailing whitespace (including newlines) is stripped from the value before storage on every note_save and note_append call. The stored value is always trimmed; it is returned as-is on load.

Read-only Flag

Any note can be marked read-only. When read_only is true:

  • note_save on an existing key returns an error
  • note_append returns an error
  • note_delete returns an error
  • note_load and note_list are unaffected
The read-only flag is never set by a tool call. It can only be toggled in the settings UI. This is intentional: it allows a user to lock a lorebook note that the LLM must be able to read but must not be able to overwrite mid-session.

The read_only field is included in the response from note_list so the model can see which notes are protected before attempting a write.

Database Schema

One new table. Added as a new numbered migration in internal/store/store.go. 

CREATE TABLE note (
    id              INTEGER PRIMARY KEY,
    key             TEXT NOT NULL,
    value           TEXT NOT NULL DEFAULT '',
    user_id         INTEGER REFERENCES user(id) ON DELETE CASCADE,
    conversation_id INTEGER REFERENCES conversation(id) ON DELETE CASCADE,
    read_only       INTEGER NOT NULL DEFAULT 0,
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL
);

-- Scope partitioning: global=(0,0), user=(user_id,0), conversation=(0,conv_id).
-- COALESCE avoids the NULL != NULL problem in SQLite unique indexes.
CREATE UNIQUE INDEX note_key_scope
    ON note(key, COALESCE(user_id, 0), COALESCE(conversation_id, 0));

-- Fast prefix lookups for note_list.
CREATE INDEX note_key_prefix ON note(key);

Constraints

  • user_id and conversation_id are mutually exclusive: at most one is non-null.
  • Global notes have both null. This is enforced in application code, not by a DB constraint.
  • Cascade deletes ensure notes are cleaned up when a user or conversation is removed.

Store functions

New file internal/store/notes.go. Public functions:

  • SaveNote(key, value string, userID, convID *int64) error
  • LoadNote(key string, userID, convID *int64) (Note, error)
  • ListNotes(prefix string, userID, convID *int64) ([]NoteRow, error)
  • DeleteNote(key string, userID, convID *int64) error
  • AppendNote(key, text string, userID, convID *int64) error
  • SetNoteReadOnly(id int64, readOnly bool) error — used by the settings UI handler only

The NoteRow type returned by ListNotes includes key, a short excerpt (first 120 characters of value), read_only, and timestamps — not the full value, to keep list responses compact.

Tool API

All five tools live in internal/server/tools.go under a notes compound group (analogous to world_state). The tool executor receives the current user ID and conversation ID from ToolContext.

note_save (key: string, value: string) → "saved"

Creates or replaces a note. If a note with this key already exists in the same scope it is overwritten. If it is marked read-only the call returns an error instead.

Parameters

keystringFull key including prefix. Must pass validation.
valuestringContent to store. Trimmed before storage.

Behaviour

  1. Validate key format. Return error if invalid.
  2. Derive scope from prefix. Resolve user_id / conversation_id from context.
  3. If a note with this (key, scope) exists and is read-only, return error.
  4. Trim value. Upsert the note, updating updated_at.
  5. Return "saved".

Errors

  • invalid key: ... — key fails validation
  • note is read-only — existing note is protected
  • no active conversation — c. key used outside a conversation context

Example

note_save("g.eldoria", "In the land of Eldoria, magic was outlawed after the Sundering...")
→ "saved"

note_save("c.session_brief", "Quest: recover the stolen crown before dawn.")
→ "saved"
note_load (key: string) → {key, value, read_only, updated_at}

Loads a single note by its exact key. Returns the full value. Returns an error if the note does not exist or is not accessible in the current context.

Parameters

keystringExact key including prefix.

Behaviour

  1. Validate key format.
  2. Derive scope; resolve context FKs.
  3. Look up the note. Enforce scope visibility (u. notes only visible to their owner).
  4. Return the note object, or error if not found.

Errors

  • invalid key: ...
  • note not found
  • no active conversation

Example

note_load("g.eldoria")
→ {
    "key": "g.eldoria",
    "value": "In the land of Eldoria, magic was outlawed after the Sundering...",
    "read_only": true,
    "updated_at": "2026-06-10T14:23:00Z"
  }
note_list (prefix?: string) → [{key, excerpt, read_only, updated_at}]

Lists accessible notes, optionally filtered by prefix. Returns key, a short excerpt (first 120 characters of the value), and metadata. Does not return full values — use note_load to retrieve content.

Parameters

prefixstring?Optional. Bare term (e.g. eldoria) or scoped prefix (e.g. g.eldoria).

Prefix expansion

If prefix is omitted or empty, all accessible notes are returned.

If prefix has no scope prefix, the server searches all three scopes. For example, eldoria matches:

  • g.eldoria and any g.eldoria.*
  • u.eldoria and any u.eldoria.* (current user only)
  • c.eldoria and any c.eldoria.* (current conversation only)

If prefix has a scope prefix (e.g. g.eldoria), only that scope is searched: matches g.eldoria and any g.eldoria.*.

SQL equivalent for a bare term T:

key = 'g.T'        OR key LIKE 'g.T.%'
OR key = 'u.T'     OR key LIKE 'u.T.%'   -- filtered to current user_id
OR key = 'c.T'     OR key LIKE 'c.T.%'   -- filtered to current conversation_id

Errors

  • invalid prefix: ... — prefix fails key-segment validation

Example

note_list("eldoria")
→ [
    { "key": "g.eldoria",            "excerpt": "In the land of Eldoria, magic was...", "read_only": true,  "updated_at": "..." },
    { "key": "g.eldoria.bestiary",   "excerpt": "Common creatures: wolf (3 HP), gob...", "read_only": true,  "updated_at": "..." },
    { "key": "u.eldoria.the_great_lake", "excerpt": "A vast freshwater lake to the no...", "read_only": false, "updated_at": "..." }
  ]
note_delete (key: string) → "deleted"

Deletes a note by exact key. Returns an error if the note does not exist, is not accessible, or is marked read-only.

Parameters

keystringExact key including prefix.

Errors

  • invalid key: ...
  • note not found
  • note is read-only
  • no active conversation
note_append (key: string, text: string) → "appended" | "created"

Appends text to an existing note non-destructively. A blank line is inserted between the existing content and the new text, so successive appends produce clearly separated paragraphs. This allows the model to add information without having to rewrite the entire note.

If the note does not exist it is created with the given text as its initial value (equivalent to note_save). Returns "appended" or "created" accordingly.

Parameters

keystringExact key including prefix.
textstringText to append. Trimmed before use.

Behaviour

  1. Validate key format.
  2. Derive scope; resolve context FKs.
  3. If the note does not exist: create it with value = trim(text). Return "created".
  4. If the note exists and is read-only: return error.
  5. Compute new_value = existing_value + "\n\n" + trim(text).
  6. Update the note. Return "appended".

Errors

  • invalid key: ...
  • note is read-only
  • no active conversation

Example

note_append("u.eldoria.the_great_lake", "The northern shore is controlled by the Fisher-Folk, a secretive clan.")
→ "appended"

Stored value becomes:
"A vast freshwater lake to the north of Eldoria.

The northern shore is controlled by the Fisher-Folk, a secretive clan."

Access Control Summary

Scope Who can read Who can write / delete Read-only overrides
g. global Any user, any LLM session Any user, any LLM session Yes — blocks all writes
u. user That user and their sessions only That user and their sessions only Yes — blocks all writes
c. conversation Sessions within that conversation only Sessions within that conversation only Yes — blocks all writes

Attempts to access a note outside the caller's visibility (e.g. another user's u. note) return note not found rather than a permission error. This avoids leaking the existence of notes the caller cannot see.

Registration and Tool Group

The five tools are registered individually in toolRegistry and executors in internal/server/tools.go. A compound group ID notes is added to the expansion logic alongside world_state, expanding to: note_save, note_load, note_list, note_delete, note_append.

TOOL_GROUPS in static/js/settings-character-edit.js gets a new entry: 

{ id: "notes", label: "Notes", description: "Note store: save, load, list, delete, and append to named notes across global, user, and conversation scopes." }

The tool display table in CLAUDE.md gains five rows (one per tool), all with no required config.

Settings UI

A new settings page at static/settings/notes.html (and corresponding JS in static/js/settings-notes.js) provides a management interface for notes outside the chat.

What users see

  • All g. global notes (any user can see and edit these)
  • All u. notes belonging to the logged-in user
  • All c. notes for conversations the user owns (read-only in the UI — conversation notes are primarily managed by the LLM during chat)

Operations available in the UI

  • Create a new note — key (with prefix), value, read-only toggle. Scope is inferred from the key prefix the user types.
  • Edit key, value, and read-only flag of any note the user can write.
  • Toggle read-only — the only place this flag can be changed.
  • Delete any note the user can write. Read-only notes cannot be deleted from the UI either.

API endpoints

New REST endpoints in internal/server/notes.go:

MethodPathDescription
GET/api/notesList notes visible to the current user. Accepts optional ?prefix= query param.
GET/api/notes/{key}Load a single note by key.
PUT/api/notes/{key}Create or update a note. Body: {value, read_only?}.
DELETE/api/notes/{key}Delete a note.
Key encoding in URLs. The key contains dots and a prefix that includes a dot (e.g. g.eldoria.bestiary). When used in the path segment the key should be URL-encoded by the client: /api/notes/g.eldoria.bestiary works as-is since dots are valid in path segments, but the router must treat the remainder of the path after /api/notes/ as a single parameter to avoid misinterpreting dots.

The PUT endpoint accepts an optional read_only boolean in the body. This is the only endpoint where read_only can be set. The tool executors never call this endpoint — they use store functions that do not expose the read_only parameter.

Logging

Follow the existing logging conventions. The REST handlers (settings UI operations) each emit one log line: 

Saving note key="g.eldoria" user_id=1
Deleting note key="g.eldoria" user_id=1
Toggling read-only key="g.eldoria" read_only=true user_id=1

Tool executor calls (LLM-driven) are not logged individually — they are high-frequency within a message loop. Tool loop activity is already captured at the message level.

Spec complete. The world-state tools (state_set etc.) are unaffected — they remain the right tool for short numeric and boolean values. Notes complement them for longer prose content.
